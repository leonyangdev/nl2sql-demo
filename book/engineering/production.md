# 从 Demo 走向生产

当前项目刻意保持小而透明：四张业务表、两个指标、本地 SQLite、简单同义词和单轮问答。生产化不是推翻它，而是沿现有边界逐层增强。

## V1 的能力边界

| 领域 | 当前实现 | 生产方向 |
|---|---|---|
| 语义识别 | 同义词子串匹配 | NER、实体链接、领域词典、澄清 |
| 指标 | 单字段 `SUM` | 表达式、派生指标、窗口、指标依赖 |
| 时间 | 年/月与少量相对词 | 日期区间、季度、财年、同比环比 |
| 检索 | 单路向量 Top-K | 混合检索、Rerank、权限过滤 |
| JOIN | 外键图最短路径 | 多路径代价、角色关系、桥接表、基数约束 |
| 生成 | 单轮 + 执行错误修正 | 语义计划、AST 生成、验证器 |
| 安全 | 正则 + 回滚 | 只读账号、AST 白名单、资源配额 |
| 对话 | 单问题 | 上下文、省略补全、澄清与指代 |
| 评测 | 人工观察 Demo | 黄金集、回归集、线上反馈闭环 |

## 演进一：把业务配置变成语义层

`business_config.py` 证明了语义治理的价值，但生产中通常需要：

- 指标平台或语义层服务作为 Metric 真相源；
- 数据目录提供表字段说明、Owner、质量与敏感级别；
- 维度和值字典来自主数据平台；
- 关系包含逻辑外键、桥表、角色扮演维度；
- 每次变更有版本、审批、生效时间和回滚能力。

推荐先定义稳定的内部语义模型，再为不同 Embedding 模型渲染检索文本。

## 演进二：引入查询中间表示

当前 `RetrievalContext` 已接近一个轻量查询计划。下一步可以让模型先生成结构化 IR，而不是直接写 SQL：

```json
{
  "metric": "sales_amount",
  "dimensions": ["product.product_name"],
  "filters": [
    {"field": "region.region_name", "op": "=", "value": "华南区"}
  ],
  "time_range": {"start": "2026-08-01", "end": "2026-09-01"},
  "order": {"by": "sales_amount", "direction": "desc"},
  "limit": 5
}
```

服务端验证 IR 后再由确定性编译器生成不同方言 SQL。这样更容易做权限注入、语义校验、缓存和多数据库适配。

## 演进三：混合检索与重排

纯向量检索擅长语义，关键词/BM25 擅长字段名、编码和缩写。生产检索常采用：

```text
向量召回 + 关键词召回 + 业务域过滤
              ↓
        合并与去重
              ↓
      Reranker / 规则重排
              ↓
     按实体类型分配配额
```

Metric 往往应有更高优先级；精确命中的字段和值也应获得加分。召回评测要按 `table/column/metric/value` 分类型统计。

## 演进四：更真实的 JOIN 规划

最短路径并不总是业务正确路径。生产图需要考虑：

- 关系置信度和来源；
- 一对多 JOIN 导致的指标膨胀；
- 同一维表在不同角色下的连接；
- 事实表之间是否需要桥接或预聚合；
- 日期生效区间、慢变维；
- 数据域和权限边界。

路径代价可以同时考虑边数、关系可信度、基数风险与业务域一致性。

## 演进五：建立评测集

至少准备四层黄金数据：

1. **意图标注**：问题对应的指标、维度、过滤、时间和排序；
2. **Schema Linking**：标准实体键和 JOIN 边；
3. **SQL 或 IR**：允许多个语义等价答案；
4. **期望结果**：在固定数据快照上的结果集。

每次修改同义词、Prompt、模型、索引参数或元数据后都跑回归。执行结果等价比字符串完全相等更有意义，但指标口径和安全约束必须单独断言。

## 演进六：可观测与反馈闭环

建议监控：

- 各阶段 P50/P95 延迟；
- Embedding 和 LLM 调用成功率、Token 与成本；
- 无 Metric、低置信度、无法连通、SQL 修正次数；
- SQL 执行失败率、空结果率和超时率；
- 用户改写、点踩、手工修正 SQL 的比例；
- 元数据变更到索引生效的延迟。

用户反馈应回流到同义词、Value 字典、Metric 描述和评测集，而不是只用于调整一个更长的 Prompt。

## 一条务实的实施顺序

1. 先选一个边界清楚的业务域，建立 30～100 个高频问题黄金集；
2. 治理核心 Metric、Dimension、Value 与 Relationship；
3. 上线只读、限额、可审计的查询执行层；
4. 用规则/IR 校验模型输出，不急着追求任意问题覆盖；
5. 根据失败样本扩展语义层和检索，而不是盲目加 Prompt；
6. 置信度不足时主动澄清；
7. 稳定后再扩数据域、复杂指标和多轮对话。
