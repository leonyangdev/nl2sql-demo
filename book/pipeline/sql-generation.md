# 4. SQL 生成、执行与总结

`agent.py` 接收 `RetrievalContext`，支持本地规则与 LLM 两种生成模式。两者共享同一套前置语义，因此可以互相对照，也可以在模型不可用时降级。

## 规则模式

`retrieval.py` 的 `plan_sql()` 将已经识别的槽位按固定模板拼装：

```text
SELECT  = 分组维度 + 指标聚合
FROM    = Metric 来源表
JOIN    = JoinGraph.plan() 的有序步骤
WHERE   = Metric 默认过滤 + 时间范围 + Value Linking
GROUP BY = 有分组意图时的维度
ORDER BY = 指标别名 + 排序方向
LIMIT   = 问题中的数量
```

优点是每个片段都能追溯，缺点是只能处理预先编码过的组合。运行方式：

```bash
python main.py ask "华南区成交额最高的商品" --rule
```

## LLM 模式如何构造 Prompt

`render_context()` 只渲染已经召回并回取过的内容，按以下区块组织：

```text
【业务数据库方言】SQLite
【可用的业务指标】公式、口径、时间字段、默认过滤
【相关数据表】表及字段
【命中的字段】物理字段与语义角色
【用户提到的取值】确定完成的 Value Linking
【允许使用的 JOIN 关系】关系图中的合法边
【已识别的时间范围】左闭右开区间
【口语说法 → 标准业务名】同义词命中
【用户问题】原问题
```

System Prompt 再加入硬约束：只允许 SQLite 单条查询；只能使用上下文中的表字段；Metric 公式与默认过滤必须保留；JOIN 不得臆造；分组、排序和 LIMIT 要服从用户意图。

::: info 为什么仍保留规则 SQL 草案
即使最终使用 LLM，检索阶段仍会生成 `context.sql`。模型调用失败时，它可以作为诊断参考；开发者也能比较 LLM 是否遗漏了某个确定性槽位。
:::

## 从模型回复提取 SQL

`extract_sql()` 兼容三种常见输出：

- ```` ```sql ... ``` ```` 代码块；
- 普通代码块；
- 裸 SQL 文本。

它会移除前导注释、末尾分号和多余反引号，再交给安全校验。

## 只读安全校验

`validate_sql()` 依次检查：

1. 内容不能为空；
2. 必须以 `SELECT` 或 `WITH` 开头；
3. 不允许分号，确保只有单条语句；
4. 拒绝 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`PRAGMA` 等关键字。

这是一道必要的 Demo 防线，但不是生产级 SQL 防火墙。更完整的防护见 [安全与正确性](/engineering/safety)。

## 执行失败后的自我修正

`generate_and_execute()` 最多尝试 `NL2SQL_LLM_MAX_ATTEMPTS` 次：

```text
模型生成
  ├─ 校验失败 → 将校验错误反馈给模型 → 重写
  └─ 校验通过 → 数据库执行
                  ├─ 执行失败 → 将 SQLite 错误反馈给模型 → 重写
                  └─ 成功 → 返回 SQL、列、行、尝试次数
```

反馈会包含上一条模型回复和具体错误，但模型每次仍需输出完整 SQL。温度固定为 0，降低同一输入下的随机漂移。

## 执行与结果总结

查询在 `sales.db` 上执行。为了防止未来代码误用，会话结束前强制回滚。执行结果先以表格打印，然后在启用总结时把这些内容交回 LLM：

- 原始问题；
- 最终 SQL；
- 列名与最多 `LLM_SUMMARY_MAX_ROWS` 行结果。

总结 Prompt 要求直接给结论、不得编造、空结果需明确说明，并限制在 120 字以内。

## 两种模式的边界

| 能力 | 规则模式 | LLM 模式 |
|---|---|---|
| 离线运行 | 是 | 否，需要 API Key |
| 可解释性 | 很高 | 依赖 Trace 与 Prompt |
| 组合泛化 | 有限 | 较强 |
| SQL 自修正 | 无 | 有 |
| 前置检索与 JOIN | 完全相同 | 完全相同 |

真正稳定的工程实践不是二选一，而是让确定性语义层约束概率式生成层，并保留可观察的降级路径。
