# 安全与正确性

NL2SQL 的风险不只在“模型可能生成 DELETE”。更常见且更难发现的是 SQL 可以执行，但用了错误指标、漏了过滤条件，或读取了用户无权访问的数据。因此需要同时处理语句安全、资源安全、权限边界与语义正确性。

## 当前 Demo 已有的防线

### 1. 生成前约束

Prompt 明确要求：

- 只生成单条 `SELECT` / `WITH ... SELECT`；
- 只能使用上下文出现过的表和字段；
- 必须遵守 Metric 公式和默认过滤；
- JOIN 只能来自允许关系；
- 时间采用左闭右开区间。

这是软约束，能降低错误率，但不能当作安全边界。

### 2. 生成后词法校验

`validate_sql()` 限制首个关键字，并拒绝分号和写操作/DDL 关键字。它能挡住直观的危险输出。

### 3. 事务回滚

查询在 SQLAlchemy Session 中执行，并在 `finally` 中 `rollback()`。即使校验未来出现疏漏，也尽量不让写入提交。

### 4. 模型空间一致性

检索前比较索引登记的 `embedding_model` 与当前 Embedder 名称。发现不一致直接拒绝召回，避免把随机相似度当成正常结果。

### 5. 业务约束前置

Metric 默认过滤、Value 显式命中和图关系属于确定性规则，不依赖模型自行记住。

## 当前校验还防不住什么

正则关键字黑名单不是完整 SQL 解析器，无法可靠处理所有方言、注释、字符串、嵌套查询与混淆写法。事务回滚也不能防止：

- 超大查询消耗大量 CPU / 内存；
- 通过函数或扩展造成副作用；
- 读取敏感表和敏感列；
- 返回过多数据造成泄漏；
- SQL 语法正确但业务口径错误。

因此生产环境不能让应用使用数据库管理员账号。

## 生产级最小防线

### 数据库权限

使用专门的只读账号，只授予允许查询的视图或 Schema。敏感字段应在数据库层脱敏或不授权，而不是只从 Prompt 中隐藏。

### AST 解析与白名单

用对应方言的 SQL Parser 解析语句树，检查：

- 根节点必须是查询；
- 实际引用的表、列都在检索上下文白名单内；
- 函数和子查询类型在允许范围；
- 禁止跨 Schema、系统表和危险扩展；
- 自动追加或限制最大 `LIMIT`。

### 执行隔离

设置查询超时、扫描行数/字节上限、并发限制和结果行数上限。高风险分析应在只读副本或数仓查询层执行，不直连生产事务库。

### 行列级权限

用户能问什么，必须由其身份和数据权限决定。常见做法是：

- 在检索阶段过滤不可见元数据；
- 在 SQL 生成后重新验证表列白名单；
- 强制注入租户、组织或数据域过滤；
- 对最终结果再做脱敏与审计。

强制权限条件不能交给 LLM 决定是否添加。

## 语义正确性检查

“可以执行”不等于“答案正确”。可以在执行前后增加：

1. **口径反查**：SQL 的聚合函数、来源字段和默认过滤是否覆盖 Metric 定义；
2. **JOIN 审计**：每个 ON 条件是否对应一条已知 Relationship；
3. **时间审计**：时间过滤是否作用于 Metric 指定字段；
4. **EXPLAIN 检查**：是否全表扫描、笛卡尔积或代价异常；
5. **结果合理性**：金额是否为异常负数、行数是否越界、分母是否为零；
6. **双路验证**：关键问题可将 LLM SQL 与规则计划或语义计划做结构比较。

## 处理歧义

当“销量”和“销售额”的召回分数接近，系统不应永远选第一名。更稳健的策略是设置置信度与差值阈值：

```text
最高分低于阈值       → 无法可靠理解，请用户澄清
Top1 与 Top2 过于接近 → 给出两个业务口径让用户选择
只有一个明显候选     → 继续生成
```

澄清不是失败，而是避免“自信地答错”的重要产品能力。

## 审计日志建议

一次问答应至少记录：

- 用户身份、问题、时间和数据域；
- 扩展后的问题与命中的别名；
- 召回实体、分数和 `entity_key`；
- Metric、Value 与 JOIN 规划结果；
- Prompt 版本、模型版本与尝试次数；
- 最终 SQL、执行耗时、扫描量和返回行数；
- 校验、修正、拒绝与用户反馈。

不要在普通日志中保存 API Key，也要评估自然语言问题与查询结果本身是否包含敏感信息。
