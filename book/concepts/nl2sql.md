# NL2SQL 到底是什么

NL2SQL（Natural Language to SQL）是把自然语言数据问题转换为可执行 SQL 的过程。表面上它像代码生成，实际上更接近“受业务语义约束的查询规划”。

用户说“2026 年 8 月华南区销售额最高的 5 个产品”，数据库只认识这些物理对象：

```text
sales_order_item.pay_amount
sales_order.order_date
sales_order.status
region.region_name
product.product_name
```

系统必须补齐自然语言与物理数据库之间缺失的语义。

## 一个问题包含哪些槽位

| 用户表达 | 系统要理解的槽位 | 本项目中的来源 |
|---|---|---|
| 销售额 | 指标与聚合口径 | `meta_metric` |
| 2026 年 8 月 | 时间范围 | `parse_time_range()` |
| 华南区 | 维度值 | `meta_value` + Value Linking |
| 产品 | 分组维度 | `meta_column.semantic_role` |
| 最高 | 排序方向 | 意图规则 / LLM Prompt |
| 5 个 | 返回数量 | `parse_limit()` |
| 多张表 | JOIN 路径 | `meta_relationship` 图 |

最终 SQL 只是这些槽位的结构化表达。难点不是写出 `SELECT`，而是确保每个槽位都选择正确。

## 为什么直接把 DDL 给大模型不够

数据库 DDL 能告诉模型 `pay_amount NUMERIC(18,2)`，却不能告诉它：

- 它代表扣除优惠后的实际支付金额；
- 业务把它称为销售额、成交额、营业额；
- 销售额只统计状态为 `completed` 的订单；
- 销售额默认使用订单日期，而不是记录创建时间；
- “华南”应映射到标准值“华南区”。

这些知识不在 Schema 中。缺少语义层时，即使 SQL 能运行，也可能在口径上完全错误。这种“语法正确、业务错误”比直接报错更危险。

## NL2SQL 的五个核心子问题

### 1. 意图理解

识别用户要查指标、明细还是实体；要整体聚合还是按维度比较；是最高、最低还是趋势。当前项目用显式规则识别时间、分组、排序和 LIMIT，让行为可观察。

### 2. Schema Linking

把“销售额”“产品”“华南”链接到数据库对象。当前项目不是只找表，而是分别召回 `table`、`column`、`metric`、`value` 四种实体。

### 3. 业务口径绑定

“销售额”被定义成 `SUM(pay_amount)` 并携带默认过滤。Metric 是业务语义进入 SQL 的主要载体。

### 4. JOIN 规划

指标位于订单明细，时间与状态位于订单头，区域和商品名称又在维表中。系统必须找到合法且尽量短的连接路径。这个问题是图问题，不是语义相似问题。

### 5. 安全执行与解释

生成后需要限制为只读单语句、捕获数据库错误、必要时修正，再把查询结果总结成用户能直接理解的答案。

## 本项目采用的混合式架构

NL2SQL 常见三种路线：

| 路线 | 优点 | 局限 |
|---|---|---|
| 纯规则 | 确定、可解释、离线 | 泛化弱，组合一多就难维护 |
| 纯 LLM | 表达灵活，开发快 | 容易臆造字段、忽略口径，难审计 |
| 元数据检索 + 受控 LLM | 兼顾泛化与治理 | 前期需要建设语义元数据 |

当前 Demo 选择第三条，同时保留规则 SQL 生成作为教学基线和离线降级。其关键不是“多调用一次模型”，而是把职责拆开：

<div class="trace-chain">确定性语义准备 → 确定性检索与结构规划 → 概率式 SQL 表达 → 确定性校验与执行</div>

## 怎样判断一个 NL2SQL 系统是否可靠

不要只统计“SQL 能不能执行”，至少要区分：

- **执行正确率**：SQL 是否能在数据库上运行；
- **结果正确率**：返回数据是否与标准答案一致；
- **口径正确率**：指标定义、默认过滤、时间字段是否正确；
- **Schema Linking 准确率**：表、字段、值是否链接正确；
- **安全率**：是否始终遵守只读、权限和数据范围限制；
- **可解释性**：能否说明每个 SQL 片段来自哪条元数据。

这个 Demo 的 Trace 与规则模式，正是为了让后四项可以被观察和验证。
